# Finding Priority এক লাইনে ব্যাখ্যা
1 executeRefund non-atomic multi-write P0 executeRefund-এ refund করার জন্য ৪–৫টা আলাদা database statement চলছে। মাঝখানে কোনো একটা operation fail করলে booking-টা refunded হয়ে যেতে পারে, কিন্তু transaction status update নাও হতে পারে। ফলে সিস্টেমের হিসাব আর আসল টাকার মধ্যে অমিল তৈরি হতে পারে।
2 Team-challenge acceptance ফি যাচাই করে না P0 Team challenge accept করার সময় fee আবার verify করা হচ্ছে না। challenge পাঠানোর সময় ৳25 charge হলেও respondTeamChallengeAction accept করে দিলে ফি ছাড়াই match confirm হয়ে যেতে পারে।
3 Wallet claim reject credit-back non-atomic P0 Claim reject করার সময় status update আর ৳25 credit-back আলাদা operation হিসেবে হচ্ছে। মাঝখানে server crash করলে status বদলে যেতে পারে, কিন্তু credit-back নাও হতে পারে। এতে ইউজারের টাকা আটকে যাওয়ার ঝুঁকি আছে।
4 Payout lifecycle নেই P1 payouts table থাকলেও owner-কে টাকা দেওয়ার পুরো flow এখনো implement করা হয়নি। অর্থাৎ owner কখন payout পাবে, কীভাবে payout request হবে এবং payout complete হলে status কীভাবে update হবে — এসব এখনো missing।
5 bKash prod IP allowlist ফাঁকা P1 BKASH_PROD_IP_ALLOWLIST=[] থাকলে বর্তমানে IP allowlist check কার্যত bypass হয়ে যাচ্ছে। ফলে request যাচাইয়ের ক্ষেত্রে মূলত HMAC signature-এর ওপরই নির্ভর করতে হচ্ছে।
6 ৫+ জায়গায় DB unique constraint নেই P1 match invitation, team invitation, wallet pending claim, payout period, report — এই ৫ জায়গায় duplicate row ঢুকতে পারে। app-level dedupe আছে, কিন্তু race condition-এ সেটা ঠেকতে পারে না।
7 Admin audit trail নেই P1 auditLogs table আছে, কিন্তু কোনো admin action এখনো এতে লেখে না। ফলে টাকা-জড়িত সিদ্ধান্তগুলো পরে trace করা যায় না।
8 Skill/position matching-এ ব্যবহারই হয় না P2 skill এখনো শুধু profile display-তে; discovery শুধু distance + kickoff দিয়ে sort করে। তাই "সঠিক দল/প্লেয়ার খুঁজে দেওয়া" — যেটা product প্রতিশ্রুতি দেয় — সেটা আসলে পূরণ হচ্ছে না।

G-1 · Admin refund execution অ-পারমাণবিক (non-atomic)FIXED — atomic multi-CTE
Evidence src/features/admin/actions.ts (executeRefund)
Was ৪–৫টা আলাদা statement: cancellation row → booking→refunded → slot reopen → transaction flip।
সমাধান হয়েছে: পুরো refund এখন একটা মাত্র multi-CTE statement — booking →refunded flip-এর RETURNING থেকে slot reopen, transaction flip আর cancellations row cascade হয়। মাঝপথে crash হলে সব একসাথে হয় বা কিছুই হয় না — হিসাব আর আর আসল টাকা আর কখনো আলাদা হবে না।

G-8 · cancelMatchAction-এ kickoff সময় যাচাই নেইP2

28 Final Conclusion

প্রশ্নটা ছিল: DeshiTurf বাস্তবে একটা football turf marketplace আর matchmaking platform হিসেবে কীভাবে কাজ করার কথা, এবং বর্তমান implementation কি সেই business logic-টা শুরু থেকে শেষ পর্যন্ত ঠিকমতো implement করেছে?

উত্তর: মূল লেনদেনের লুপ — turf publish → slot → hold → pay → confirm → play → settle → ERP — সত্যিই শক্তভাবে বানানো হয়েছে। double-booking তিন স্তরে অসম্ভব, price কখনো client-কে trust করা হয় না, wallet-এর প্রতিটি movement এক statement-এ idempotent, আর RBAC server-authoritative। সাধারণত যে মানের কাজ দেখা যায়, এটা তার অনেক ওপরে।

কিন্তু ব্যবসা হিসেবে পুরো চক্রটা এখনো অসম্পূর্ণ: (১) জমা হওয়া টাকা owner-এর হাতে পৌঁছানোর ব্যবস্থা (payout) এখনো বানানোই হয়নি; (২) টাকার তিনটা পথ (admin refund, challenge fee, claim reject) non-atomic — মাঝপথে crash হলে হিসাবে অমিল হয়; (৩) "matchmaking" নামে যে বুদ্ধিমান matching বোঝায়, তা এখনো শুধু listing-এ নামিয়ে আনা; (৪) বাস্তব জগতের ঘটনা — reschedule, no-show, overlap, dispute-এর পরে জানানো — কোনোটাই modeled নয়।

রায়: তিনটা P0 ঠিক করে, payout চালু করে, আর ৫টা unique index বসালে platform-টা নিশ্চিন্তে চালু করা যায়। এরপরের প্রতিযোগিতামূলক লাফটা হবে matchmaking-কে আসলের matching বানানো।
