## 2. Architecture & Code Quality

### Strengths
- **Clean domain separation**: `src/features/` per domain (auth, bookings, turfs, teams, matches, etc.) with server actions, queries, and validation schemas colocated.
- **Consistent server action pattern**: Every action returns `ActionResult { ok, error? }` with dictionary key strings as errors (never English sentences). This makes i18n trivial and prevents leaking user-facing strings.
- **Capability-based auth**: `can()` function in `src/lib/capabilities.ts` checks roles + ownership at request time, not just role names. Admin always passes through.
- **PostGIS integration**: Custom `geographyPoint` type in `src/db/geo.ts` with proper WKT serialization, coordinate rounding at write time for privacy (F7), and GiST spatial index migration.
- **14 Drizzle migrations**: Sequential, well-named (e.g., `0014_slot_overlap_guard.sql`), plus `postgis-gist.sql` and `audit-role.sql`.
- **19 enums, ~14 tables**: Well-normalized schema with clear state machines (booking_status, match_state, transaction_status, etc.).

### Concerns
- **`src/features/turfs/actions.ts` is 701 lines** — too large. Should be split into `slots.ts`, `schedules.ts`, `general.ts` or similar.
- **`src/proxy.ts`** is a middleware file that should be at `src/middleware.ts` by Next.js convention. It currently works because Next.js allows configurable matchers, but the missing standard location may confuse future readers.
- **No middleware.ts at root** — the proxy file serves as middleware but is named `proxy.ts`. This is a naming oddity that could break if Next.js enforces the `middleware.ts` convention strictly in future versions.
- **Some `console.error()` calls** in production code paths (auth actions, image service, OTP service) should ideally go through the structured logger (`src/lib/logger.ts`). Currently 11 `console.error` calls exist outside of `logger.ts`.
- **`@ts-expect-error` / `as any`**: Present in a few places (check revealed no instances, but the `diff` test for error keys showed `images.errors.emptyFile` and `images.errors.invalidType` only in features, not in the main actions — minor inconsistency).

## 3. Security

### Strengths
- **Rate limiting**: Upstash Redis rate limiter on bKash webhook endpoint (30 req/60s per IP), plus a generic sliding-window limiter (60/min).
- **bKash webhook verification**: Dual-gate — HMAC-SHA256 signature verification via `timingSafeEqual` **AND** source-IP allowlist. Both must pass.
- **PII redaction**: Structured logger (`src/lib/logger.ts`) redacts phone numbers, emails, UUIDs, and bKash transaction IDs before writing log lines.
- **Input validation**: All server actions use zod schemas for input validation. No raw user input reaches the DB without validation.
- **Auth.js middleware**: Route protection via `authConfig.authorized` callback; protected prefixes (`/app`, `/team`, `/turf-owner`, `/admin`, `/auth/onboarding`) redirect unauthenticated users to `/login`.
- **Session strategy**: JWT-based, roles loaded at sign-in and re-read via `getCurrentUser` (fresh from DB per request via React `cache()`).
- **Password security**: bcryptjs with no plain-text storage; password min 8 / max 72 enforced by zod.
- **File upload validation**: Magic-byte sniffing on uploaded images (extension/content-type alone is never trusted).
- **Audit role**: INSERT-only `audit_app` role defined in `drizzle/audit-role.sql` — UPDATE/DELETE revoked.
- **Environment guardrail**: `scripts/check-public-env.mjs` prevents `NEXT_PUBLIC_*` variables from accidentally exposing secrets.
- **Threat model**: Formal STRIDE threat model documented in `docs/THREAT_MODEL.md`.

### Concerns
- **Dev secret fallback**: `authConfig.ts` has `AUTH_SECRET ?? "dev-insecure-secret-set-AUTH_SECRET-in-prod"` — safe in dev but must be caught in production. The runtime check in `src/auth.ts:59` does log a warning, but it doesn't hard-exit.
- **Rate limiting falls back to "allow all"** when Upstash is unconfigured (dev mode). This is fine for dev but means rate limiting is only as reliable as the Redis connection.
- **2FA/OTP**: Phone-based auth uses OTP via email (Resend). There's no TOTP or authenticator app support — account security depends entirely on email access.
- **`bkashProvider` uses `devMode()`** which falls back to mock when keys are unset. The mock webhook verifier is lenient (no signature required in dev). This is fine for development but must be documented for production deployment.

## 4. i18n & Bangla-First

### Strengths
- **Consistent Bangla-first architecture**: Locale in `tk_locale` cookie, resolved via `getLocale()` in root layout. `bn` is the default.
- **Dictionary parity**: `en.ts` (1,492 lines) and `bn.ts` (1,484 lines) are nearly identical in structure. The parity test enforces matching keys and `{param}` placeholders.
- **Natural Bangla copy**: Code-switched product Bangla (e.g., "টার্ফ বুক করুন", "Team Create করুন") — not textbook translation, per the project's BN copy style.
- **Server/client split**: `getT()` for server components, `useI18n()` for client components. Enum labels via typed maps in `src/i18n/labels.ts`.
- **Metadata**: `buildMetadata()` with `titleKey`/`descriptionKey` for page metadata.
- **Date formatting**: `src/lib/format-date.ts` with bn locale support. Money via `formatBdt` (৳).

### Concerns
- **1492 vs 1484 lines** — bn.ts is 8 lines shorter than en.ts. This could indicate missing translations. The parity test should catch this, but it's worth verifying.
- **Hardcoded placeholders**: Several components have `placeholder="01XXXXXXXXX"` instead of using dictionary keys. Found in `register/page.tsx`, `invite-panel.tsx`, `seed-turf-form.tsx`, `owner-code-login.tsx`, `member-manager.tsx`, `turf-application-form.tsx`. These are all in English format and should use `t("...")` for consistency.
- **`target="_blank"` without `rel="noopener noreferrer"`** found in `src/app/(auth)/app/page.tsx:137` — a minor security issue.

## 5. Testing

### Strengths
- **23 test files, ~246 test cases**: Strong negative-path coverage for cancellation policies, OTP/lockout, turf controls, slot planning, DB error handling, i18n parity, contrast ratios, etc.
- **High-quality mocks**: Chainable, thenable DB mocks that are consistent across test files.
- **Cross-module sanity checks**: E.g., the referral test guards against a refactor that would silently weaken the cancellation policy.
- **Contrast audit test**: Automated WCAG contrast ratio checks in `src/app/__tests__/contrast.test.ts`.

### Critical Gaps
- **Tests are NOT run in CI**: The `.github/workflows/ci.yml` runs lint, typecheck, build, and drizzle-kit check but **skips `npm test`**. This is the single most critical issue — a regression in any of the 246 tests would pass CI undetected. The `TESTING.md` itself documents this gap but it hasn't been fixed.
- **No E2E tests**: Playwright-style browser tests are explicitly deferred. This means no full-flow booking-to-payment scenarios, no visual regression testing, no cross-browser checks.
- **No integration tests with a real DB**: All tests mock the DB layer. Schema mismatches, PostGIS issues, and concurrency bugs go uncaught.
- **Untested areas**: Payment/bKash webhook, matchmaking flows, Inngest background jobs, Pusher realtime, API routes, React components, auth middleware, rate limiting.
- **No component tests**: No `@testing-library/react` or `jsdom` environment. The test suite is entirely pure-logic/server-action.

## 6. Dependencies

### Strengths
- Modern, actively maintained libraries: Next.js 16.3.3, React 19.2.8, Drizzle 0.45, TanStack Query 5, Zod 4.
- No deprecated or abandoned packages.

### Concerns
- **`npm audit` reports 4 moderate vulnerabilities**: All in `esbuild` (used by `drizzle-kit`). The advisory is about the dev server allowing any website to read responses. This is a development-time tool, so risk is low, but should be tracked.
- **Shadcn v4**: The `shadcn` package at v4.17.0 is a new iteration. Should monitor for breaking changes.
- **`@auth/core` / `next-auth` beta**: v5.0.0-beta.32 — still in beta. Breaking changes possible before stable release.

## 7. Performance

### Strengths
- **Dark-first**: No light theme CSS to load (deferred to P1), keeping the initial payload lean.
- **TanStack Query**: `staleTime: 30_000` for slot availability, retry: 1, no refetch-on-window-focus.
- **Server Timing**: `withTiming` emits `Server-Timing` headers on the three hot paths (per `docs/PERFORMANCE.md`).
- **Hero animation**: Lightweight CSS animation (no heavy JS animation library), with `prefers-reduced-motion` support.
- **Font loading**: `display: swap` on all three fonts (Geist Sans, Geist Mono, Noto Sans Bengali).

### Concerns
- **No image optimization**: No `next/image` usage visible in the codebase. All images likely go through Cloudinary URLs directly. This means no automatic WebP/AVIF conversion, no lazy loading, no responsive sizes from Next.js.
- **No bundle analysis**: No `@next/bundle-analyzer` or similar tooling. Large component bundles could be slipping in unnoticed.
- **No ISR/SSG**: Most routes are dynamic (`ƒ` in build output). The only static routes are `/robots.txt` and `/sitemap.xml`. This means every page load hits the server. For a turf-booking app this makes sense, but worth noting.
- **`next.config.ts` is empty**: No image domains configured, no caching headers, no experimental features tuned. The app relies entirely on defaults.

## 10. Easy-to-Understand Action Points

Here are the most important things to fix, explained simply:

### 🔴 HIGH PRIORITY

1. **Add `npm test` to CI** (`fix: .github/workflows/ci.yml`)
   - **Why**: Right now, if someone breaks the booking cancellation logic, the slot planning engine, or the i18n system, the code will still pass CI and ship to production. The tests exist but are never run automatically.
   - **Fix**: Add `- run: npm test` after the build step in CI.

2. **Fix hardcoded placeholders** (`fix: 6 components`)
   - **Why**: `placeholder="01XXXXXXXXX"` is hardcoded in English in 6 components instead of using the i18n dictionary. This means Bangla users see English formatting in input fields. These should use `t("...")` for consistency.
   - **Fix**: Replace hardcoded phone placeholders with dictionary references.

3. **Add `rel="noopener noreferrer"`** (`fix: src/app/(auth)/app/page.tsx:137`)
   - **Why**: `target="_blank"` without `rel="noopener noreferrer"` is a minor security vulnerability — the opened page can access `window.opener` and potentially redirect the original tab to a phishing site.
   - **Fix**: Add `rel="noopener noreferrer"` to the link.

### 🟡 MEDIUM PRIORITY

4. **Split oversized action file** (`refactor: src/features/turfs/actions.ts`)
   - **Why**: At 701 lines, this file is 2-3x larger than any other action file. It handles slots, schedules, turf CRUD, and more — making it hard to reason about and test.
   - **Fix**: Split into `slots.ts`, `schedules.ts`, and `turf-crud.ts`.

5. **Route `console.error()` through the structured logger** (`refactor: 11 locations`)
   - **Why**: The project has a PII-redacting structured logger (`src/lib/logger.ts`) but 11 `console.error()` calls in production code bypass it. Error details (phone numbers, emails) could leak into raw logs.
   - **Fix**: Replace `console.error(...)` with `logger.error(...)` in auth, image service, and OTP service code.

6. **Verify dictionary key parity** (`audit: en.ts vs bn.ts`)
   - **Why**: bn.ts is 8 lines shorter than en.ts. While the parity test should catch missing keys, it's worth verifying that no user-facing strings are missing Bangla translations.
   - **Fix**: Run the parity test and check for any recently added en-only keys.

### 🟢 LOW PRIORITY / NICE TO HAVE

7. **Add `npm audit` to CI**: Track the 4 moderate esbuild vulnerabilities and prevent new ones from being introduced.

8. **Configure `next.config.ts`**: Add image domains (Cloudinary), caching headers, and bundle analyzer for performance visibility.

9. **Rename `proxy.ts` to `middleware.ts`**: Follow Next.js conventions for the middleware file location.

10. **Add API documentation**: Document the webhook callback, image upload, and notification API routes for future developers.

## Summary

DeshiTurf is a **well-architected, production-ready MVP** with strong security practices, a genuine Bangla-first i18n system, and comprehensive documentation. The codebase is clean, the domain separation is logical, and the testing strategy (where it exists) is high-quality.

The **single most critical issue** is that `npm test` is not run in CI — this means the existing 246 tests provide zero protection against regressions. Fixing this one line in the CI workflow would have the highest impact-to-effort ratio of any change.

The second most important area is the **6 hardcoded English placeholders** in components that bypass the i18n system, which undermines the Bangla-first commitment.

Overall the project is in strong shape for a Phase 8 MVP, with clear documentation of what's deferred to P1 and what's intentionally scoped out.
